VAE Condition Ablation

The model sees three frames F0, F1, F2 of a clip and generates the next frame F3. The ViT always gets all three. Only the frames that are also encoded by the VAE and fed to the diffusion decoder change: none, F0 only, or all three.

What changed from the 5-datapoint version

The run now covers {{N}} datapoints (the first 5 are the earlier ones). Two earlier statements did not hold up and are replaced below: "all three frames is better than F0 only" (at {{N}} datapoints the two are indistinguishable on semantic similarity), and the 672×384 outputs being representative (that size has a one-patch mismatch with the VAE condition, see "Why 672×384 looks cropped").

Results at a glance

  • No VAE condition fails at every size. The input scene is not reproduced in any of the {{N}} datapoints. Gray fields, portraits, text posters, another object or another room. By CLIP similarity to F2, 27 to 30 of {{N}} outputs fall below 0.75, against 1 to 9 for the conditioned settings.
  • F0 only and all three frames are equivalent semantically. CLIP similarity to the ground truth differs by 0.007 to 0.013 with a standard error of 0.009 to 0.016, and neither wins more than 23 of {{N}} datapoints at any size. In pixels, all is closer to the ground truth (35 of {{N}} datapoints at 688×400), because it is handed F2 itself.
  • Output size matters more than the condition. At 672×384, 10 of {{N}} outputs have layout artifacts (panels, caption strips, shifted or cropped content) in both conditions. At the matched sizes it is 1 to 3. At 832×480 native the artifacts change type: 8 duplicated objects (5 with first, 3 with all) appear that do not occur at the other sizes.
  • 688×400 is the safest size here. It has the highest CLIP scores for both conditions (all: +0.030 ± 0.008 over 832×480) and no duplicated objects. It is the default in the gallery.
  • No condition forecasts better than copying the last frame. The trivial "copy F2" baseline scores CLIP 0.974 and pixel distance 10.2 to the ground truth. Every generated setting is farther (CLIP 0.83 to 0.89, pixel distance 25 to 47). Visible physical changes exist (seedling grows, light changes color, the window turns translucent) but are the exception.

Why 672×384 looks cropped

Nothing in preprocessing crops. The full frame reaches both branches. The ViT gets it squashed to 448×448 (an aspect change that is standard for every edit call). The VAE branch gets it resized to 688×400, which is 43×25 condition tokens at 16 px per token, while the 672×384 output grid has 42×24 tokens. 672×384 has an area of 258,048 px, just under the processor's 262,144 px minimum, so the condition path scales it up and rounds one way while the output path keeps 672×384. My reading is that the decoder then places condition and target tokens one row and one column apart in its shared coordinate system, which shows up as shifted, bordered or caption-strip frames. 688×400 and 832×480 are multiples of 16 inside the processor's pixel range, so neither path changes them.

Tension F2: original frame, our 672×384 resize, what the ViT receives, what the VAE branch receives. Read from pixel_values and pixel_values_gen by inspect_preproc.py. The rounding difference is inferred from the observed sizes, not read from the processor source, and I did not isolate which tokens the decoder misplaces. The evidence is that the artifact rate falls from 10 of {{N}} to 1 to 3 when the sizes match.

How the prompts are handled

The text is T5's own user turn, identical for the three conditions and the three sizes. The pipeline receives image=[[F0, F1, F2]], so each <image> slot is filled and all three frames go through the ViT.

Here are three consecutive frames sampled from a video clip, in chronological
order and equally spaced in time.

Caption: <PhysicTran38K caption>
F0: <image>
F1: <image>
F2: <image>
GAP: 1.0 s (time between consecutive frames)

Generate the next frame F3, which comes one GAP after F2.

The stock processor builds three classifier-free-guidance rows from it:

The PhysicTran38K caption states the outcome ("the final frame shows a sustained dormant posture…"), so the text alone can describe F3 in all three conditions. This is the same caption caveat as in T5's docs. It does not prevent the failures of none.

How the conditions are implemented

The stock pipeline VAE-encodes every earlier image (_prepare_diffusion_inputs → conditional_image). gen.py wraps that method and slices only the VAE-side tensors conditional_image and image_grid_thw_gen_cond to the first 0 / 1 / 3 frames, kept index-aligned. The ViT tensors (pixel_values, encoder_image_token_mask, image_fhw_cond) are never touched. check_inputs.py confirms the counts above on real inputs, and every run logs them in outputs/_meta/.

Two stock-code problems had to be patched at runtime (patches.py; the package is not edited):

  • Processor assert. With 3 frames, the unconditional row (no <image> slots) trips only 1 fake picture in pure text input. That row's image data is discarded anyway, so the assert is skipped for it.
  • Decoder crash for more than one VAE image. _prepare_hidden_inputs_anyres adds a vector of per-image token counts where it needs their sum, so it raised TypeError: only integer tensors of a single element can be converted to an index at 3 images. The patch adds .sum() at the two slice sites. This only affects all. Training code only passes one condition image per sample, so the base model has probably never seen several VAE frames at once.

Limits and reproduction

  • {{N}} datapoints from one source (synthetic PhysicTran38K clips, one gap), one noise seed, no repeats. Differences of a few hundredths in CLIP are inside the noise.
  • The matched sizes were chosen after seeing the first run, so the size effect is a fix found post hoc, not a pre-planned arm. The failure tags are my reading, not a blinded rating.
  • none, first and all also differ in how many condition tokens the decoder attends to, not only in what information they carry. This run does not separate the two.
