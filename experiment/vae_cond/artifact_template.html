VAE Condition Ablation

The model sees three frames F0, F1, F2 of a clip and generates the next frame F3. The ViT always gets all three. Only the frames that are also encoded by the VAE and fed to the diffusion decoder change.

Correction after the size test

The first run asked for a 672×384 output, but the pipeline feeds the VAE a 688×400 condition. That one-patch size mismatch caused the cropped, shifted and paneled outputs (the tension strip pushed to the bottom edge, plants inside gray borders). When the output size equals the condition size, those artifacts disappear. The comparison below therefore defaults to 832×480, the native frame size; 688×400 and 672×384 stay one click away in the gallery.

Results at a glance

  • No VAE condition fails at every size. The decoder does not reproduce the scene: gray fields, a cartoon face, a text poster, a lone yellow flower or fruit. Sometimes the object is on topic, never the scene.
  • With a matched size, one VAE frame (F0) already gives a coherent frame in 5 of 5 datapoints at 832×480 (4 of 5 at 688×400, where tension is blurred and loses the hands).
  • All three frames is the better setting. It is closer to the ground truth in pixels at both matched sizes (table), keeps the hands in the tension frame at 688×400 where first loses them, and brings more yellow flowers in the plant clip. The gap is moderate and rests on 5 examples.
  • Neither shows the physical change reliably. Outputs are still about as close to F2 as to the ground truth (all at 688×400 is even closer to F2: 17.7 vs 20.4), so mostly they extend the last frame. The visible exceptions are the extra flowers and a warmer, more yellow fruit at 832×480.

Why the first run was cropped

Checking the preprocessing for cropping (CPU-only, no weights) showed no crop anywhere: the full frame reaches both branches. The ViT gets it squashed to 448×448 (an aspect change that is standard for every edit call). The VAE branch gets it resized to 688×400, which is 43×25 condition tokens at 16 px per token. The 672×384 output grid has 42×24 tokens. The decoder places condition and target tokens in one shared coordinate system, and a grid that is off by one row and column puts the content in the wrong place, which looks like cropping. 688×400 and 832×480 are multiples of 16 and make both grids equal.

Tension F2: original frame, our 672×384 resize, what the ViT receives, what the VAE branch receives. The content is complete in all four. Read from pixel_values / pixel_values_gen by inspect_preproc.py. The mismatch explanation fits all the evidence, and matching the sizes removes the artifacts, but I did not isolate which tokens the decoder misplaces.

How the prompts are handled

The text is T5's own user turn, identical for the three conditions and the three sizes. The pipeline receives image=[[F0, F1, F2]], so each <image> slot is filled and all three frames go through the ViT.

Here are three consecutive frames sampled from a video clip, in chronological
order and equally spaced in time.

Caption: <PhysicTran38K caption>
F0: <image>
F1: <image>
F2: <image>
GAP: 1.0 s (time between consecutive frames)

Generate the next frame F3, which comes one GAP after F2.

The stock processor builds three classifier-free-guidance rows from it:

The PhysicTran38K caption states the outcome ("the final frame shows a sustained dormant posture…"), so the text alone can describe F3 in all three conditions. This is the same caption caveat as in T5's docs. It probably narrows the gap between conditions, but it does not prevent the failures of none.

How the conditions are implemented

The stock pipeline VAE-encodes every earlier image (_prepare_diffusion_inputs → conditional_image). gen.py wraps that method and slices only the VAE-side tensors conditional_image and image_grid_thw_gen_cond to the first 0 / 1 / 3 frames, kept index-aligned. The ViT tensors (pixel_values, encoder_image_token_mask, image_fhw_cond) are never touched. check_inputs.py confirms the counts above on real inputs, and every run logs them in outputs/_meta/.

Two stock-code problems had to be patched at runtime (patches.py; the package is not edited):

  • Processor assert. With 3 frames, the unconditional row (no <image> slots) trips only 1 fake picture in pure text input. That row's image data is discarded anyway, so the assert is skipped for it.
  • Decoder crash for more than one VAE image. _prepare_hidden_inputs_anyres adds a vector of per-image token counts where it needs their sum, so it raised TypeError: only integer tensors of a single element can be converted to an index at 3 images. The patch adds .sum() at the two slice sites. This only affects all; none and first run on the stock path. Training-time code only passes one condition image per sample, so the base model has probably not seen several VAE frames at once.

Limits and reproduction

  • 5 datapoints, one noise seed, no repeats. Differences between first and all are within what another seed could change. The matched sizes were chosen after seeing the first run, so the size effect is a fix found post hoc, not a pre-planned arm.
  • none, first and all also differ in how many condition tokens the decoder attends to, not only in what information they carry. This run does not separate the two.
