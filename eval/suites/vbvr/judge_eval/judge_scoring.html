How Each Task Is Scored: Rule vs. Judge

For each of the 9 active tasks with real eval data, this page explains BOTH ways InternVL-U's generations get scored: the existing rule-based detector (a short plain-language summary of what its code actually checks) and a pure Qwen3-VL-30B-fp8 judge built as a like-for-like alternative — same sub-criteria and weights the rule-based evaluator uses (its active, non-dropped task_specific dimensions — see evaluators/llm_judge_full.py), classified into wrong / partial / correct per criterion rather than a bare number, then combined with the same weights. It's a straight swap of detector-code for judge-vision, not a different rubric. Validated on the same "Representative" / "Worst-scoring" examples already shown in the target-frame-prediction results artifact, so rule vs. judge scores are directly comparable on identical images.

2026-08-26/27 revision, round 2: auditing fresh random samples by eye (not just aggregate stats) surfaced two more issues, on top of the visual-coherence gate described in each task's card below. (1) maze's rule-based score had a real bug — short path stubs that never reached the end scored 0.4–0.71, now fixed with a path-coverage gate (see that task's card); rule and judge means for this task now agree closely (0.03 vs 0.03). (2) The judge had a real, harder-to-fix weakness on tasks needing precise grid-cell or tile-position verification (grid_shift, rotation_puzzle): it would confidently mark position-precision criteria "correct" with a detailed-sounding but fabricated justification (e.g. "moved exactly 2 cells left, landing in the correct grid cells") on candidates that visibly don't match the ground truth. A prompt instruction requiring element-by-element comparison helped partially; sending higher-resolution images (900px vs 512px) made no difference. For grid_shift's and rotation_puzzle's position-precision-style criteria specifically, trust the rule-based score over the judge's — the rule side is deterministic pixel comparison and held up under repeated manual spot-checks.
A stronger fix was tried and reverted: forcing the judge to write a concrete "observation" for each criterion before its verdict (a standard LLM-grounding technique) fixed several individually-flagged false positives when spot-tested against known problem cases. But re-run at FULL SCALE (all 900 real generations, not just the cases it was tuned against) it was a clear regression: judge means jumped up across nearly every task (e.g. maze 0.06→0.63) and rule-vs-judge correlation dropped (0.26→0.17). Checked directly: on a maze image with nothing drawn at all (just walls and the end flag, no path, no start marker), the judge scored it a perfect 1.0 with a detailed, entirely fabricated description ("a complete, valid path of yellow dots connecting start to end"). 180/900 samples (20%) showed this pattern — forcing a plausible-sounding justification made the model MORE prone to confabulating support for a verdict it was already inclined toward, not more grounded. Reverted; kept the lighter element-by-element instruction from the previous paragraph, which tested fine at full scale. Lesson: a prompt change validated only against previously-flagged failure cases is confirmation-biased and does not predict full-corpus behavior — check a fresh random sample before committing to a full re-score.
Headline finding: the judge is much harsher than the rule-based system on partial-success cases — on 11 of 18 examples here it scored 0 where the rule-based system gave partial credit for a close-but-imperfect match, behaving almost binary (correct / not) rather than continuous, even with the 3-level wrong/partial/correct scale (this isn't a granularity artifact of a 0-100 scale). It also isn't infallible in the other direction: on grid_shift's worst-scoring example, the judge scored a clearly wrong layout as a perfect 1.000 ("All blocks moved upward by exactly 3 steps, matching the gro…") when the rule-based system correctly caught it at 0.000 — see that task's card below for the actual images.

Knowledge

ball_bounces_given_time

A ball starts at a marked position with a direction arrow, and is supposed to bounce off the boundary walls a stated number of times following elastic collision physics (angle of incidence = angle of reflection), ending at a specific final position. Note: this scene shows only the ball's resting position, not a drawn bounce path -- you cannot verify bounce count or reflection angles from a single static image, only final position.

How the rule-based evaluator actually works

final_position reuses _track_ball_positions (Hough circle detection, dark-blob contour fallback), run on the single final frame only.

Also applies to every task above (added 2026-08-26): a generic _visual_coherence_penalty gate runs after task_specific is computed, regardless of which detector produced it. Real (untrained-base-model) generations are often visually incoherent in ways clean synthetic test pairs never are — e.g. a ball_bounces_given_time sample scored 0.995 where the "ball" was actually a thin orange ring of dots with no resemblance to the GT's solid pink circle, and a shape_color_then_move sample scored 1.0 with garbled text baked into wrong-colored shapes — both cases the per-task detectors' loose color/position thresholds were coincidentally satisfied by, and both a VLM judge immediately called wrong on sight. The gate computes what fraction of the candidate's foreground pixels (by area, and separately by connected-component — so a small wrong object can't hide inside a large shared correct one, like a static border) have no close match anywhere in that sample's own GT palette, and discounts task_specific accordingly. Verified as a true no-op on every task's clean synthetic pairs (penalty stays 1.0) before trusting it on real data; raised rule-vs-judge Spearman correlation across 900 real generations from 0.14 to 0.26.

Criteria (from the current rule-based evaluator)

  • final_position100%
    • correctThe ball's final position in the candidate is essentially the same location as in the ground truth (small pixel offset, clearly the same resting spot).
    • partialThe ball is in roughly the right region/quadrant of the frame but noticeably off from the exact ground-truth position.
    • wrongThe ball is in a clearly different location, missing entirely, or the scene doesn't show a plausible resting ball at all.

Real (untrained-base-model) generations are often visually incoherent in ways clean synthetic test pairs never are — e.g. a ball_bounces_given_time sample scored 0.995 where the "ball" was actually a thin orange ring of dots with no resemblance to the GT's solid pink circle, and a shape_color_then_move sample scored 1.0 with garbled text baked into wrong-colored shapes — both cases the per-task detectors' loose color/position thresholds were coincidentally satisfied by, and both a VLM judge immediately called wrong on sight. The gate computes what fraction of the candidate's foreground pixels (by area, and separately by connected-component — so a small wrong object can't hide inside a large shared correct one, like a static border) have no close match anywhere in that sample's own GT palette, and discounts task_specific accordingly. Verified as a true no-op on every task's clean synthetic pairs (penalty stays 1.0) before trusting it on real data; raised rule-vs-judge Spearman correlation across 900 real generations from 0.14 to 0.26.
